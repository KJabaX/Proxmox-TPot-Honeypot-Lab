# SMB stream analysis

## Method

The supplied Dionaea bistream was treated as untrusted data. Its single Python-style assignment was parsed with `ast.parse`, and only the literal value was decoded with `ast.literal_eval`. The capture was not executed, imported, replayed or sent to a target.

The recording contains 13 direction-labelled chunks. Chunks are not SMB messages or TCP packets: one chunk may contain several messages. Bytes were concatenated separately for each direction, then split using the four-byte session framing header and its declared length. Every decoded message had an SMB1 signature, and both directional buffers ended at a complete frame boundary.

This validates the framing of the available recording; it does not establish that the recording contains every byte or connection involved in the wider activity.

## Observed message counts

| Command | Client to honeypot | Honeypot to client |
|---|---:|---:|
| NEGOTIATE (0x72) | 1 | 1 |
| SESSION_SETUP_ANDX (0x73) | 1 | 1 |
| TREE_CONNECT_ANDX (0x75) | 1 | 1 |
| NT_TRANSACT (0xa0) | 1 | 1 |
| TRANSACTION2_SECONDARY (0x33) | 16 | 0 |
| ECHO (0x2b) | 2 | 2 |
| **Total** | **22** | **6** |

The original text representation is 81,187 bytes. Decoded directional data, including session framing, totals 66,916 bytes inbound and 368 bytes outbound. These are application recording sizes, not TCP packet counts or on-wire byte totals.

## Sequence and interpretation

The client negotiates SMB1 using `NT LM 0.12`, opens a session, and requests the `IPC$` share. The setup contains the client-provided string `pysmb`; it is not a reliable identification of the exact tool or actor.

An NT_TRANSACT request declares 65,558 bytes of transaction data and supplies the first 2,000 bytes. Fifteen subsequent TRANS2_SECONDARY messages each carry 4,096 bytes; the final continuation carries 2,118 bytes. Their displacements produce contiguous data:

`2,000 + (15 × 4,096) + 2,118 = 65,558`

Two ECHO exchanges occur during the transfer. All six recorded server responses have a zero status field. The short NT_TRANSACT response is not evidence that the later exploit data was successfully processed. There is no recorded response after the final continuation.

## FEA observations

The reconstructed data begins with an FEA list size field of 65,536 bytes. Inspection identified 600 empty attributes, followed by a large attribute containing repeated `A` bytes, another structured attribute, and a trailing malformed attribute header. The final header declares more data than remains in the buffer.

A size discrepancy or a TRANS2_SECONDARY message alone would not establish exploitation. Here, the mixed NT_TRANSACT-to-TRANS2_SECONDARY sequence, the large transaction and the crafted FEA layout jointly provide strong support for an EternalBlue-like exploitation attempt.

The bytes support a protocol-level classification. They do not establish successful memory corruption, shellcode execution, a specific exploit implementation, or a malware family.

## Honeypot responses

The service advertises `Windows 7 Professional`. This is a response generated by the honeypot, not evidence that the actual host runs Windows. Successful negotiation, session setup and share responses describe the emulated service's behaviour; they do not prove compromise of the underlying system.
